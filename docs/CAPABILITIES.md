# AirPlay and B7 media capabilities (Milestone 3, phase 2)

This assessment is for the fork at the pinned UxPlay 1.74 source commit `9f3c2bbc658645533fa1057e76c29ec8c947fa0f`, on LG OLED B7 / Rockhopper 3.9.0. A sender's ability to connect is evidence for that interaction, not certification of every feature associated with an AirPlay version.

| Path | Current implementation and evidence | Status |
| --- | --- | --- |
| Screen Mirroring | RAOP mirror callbacks deliver H.264 access units and remote PTS. `video_set_codec` accepts H.264 only. The default advertises 1280×720 at 30 FPS; the selectable experimental profile advertises 1920×1080 at 30 FPS. Actual SPS dimensions can differ and are shown separately. User tested 720p mirroring and photo/video content shown through mirroring on the B7. | 720p/30 working; 1080p/30 code path built but B7 runtime untested. |
| AirPlay audio | The RAOP audio callback accepts PCM and compressed audio codes; the app decodes ALAC, AAC-LC and AAC-ELD with pinned FFmpeg and feeds 44.1 kHz stereo PCM to Starfish. Mirroring audio works on B7. Audio-only sessions have no playback startup path in this fork: `main.cpp` waits for a video keyframe. | Mirroring audio works; standalone audio-only playback unsupported. |
| AirPlay 2 | The pinned UxPlay core has partial modern pairing/mirroring/audio protocol support, and its default DNS-SD mask includes several audio-related bits. This fork forces feature bit 27 (legacy pairing), bit 42 (screen multi-codec) off, and does not implement CoreUtils pairing, PTP, AirPlay 2 video queue or multiroom behavior. | Partial compatibility with modern senders; **not** full AirPlay 2. |
| Direct photo/video streaming | `raop.c` logs “ignoring AirPlay video streaming request (use option -hls to activate HLS support)” when the HLS switch is false. This fork never enables it, has no direct-media playback/render callbacks, and advertises video/HLS feature bits 0 and 4 as off. | Unsupported. Photos/video visible during mirroring use the mirroring path. |
| HLS | Pinned upstream UxPlay offers `-hls` with documented YouTube-app HLS support, using a GStreamer player. This fork does not enable that path or package a player for it. HLS is not equivalent to all Photos-app or AirPlay 2 direct-media requests. | Unsupported; requires separate design and firmware testing. |
| HEVC / 4K | The pinned core can parse HEVC mirror packets, but this fork rejects `VIDEO_CODEC_H265`, drops `is_h265` frames, leaves multi-codec bit 42 off, and bounds H.264 SPS dimensions to 1920×1920 / 2,073,600 pixels. Video packets are capped at 1 MiB for 720p or 2 MiB for 1080p; Starfish uses matching source-buffer limits. | Unsupported; do not offer 4K as a working option. |
| HDR10, HLG, BT.2020, Dolby Vision | No HDR transfer/primaries/matrix/mastering metadata is extracted from the incoming stream or conveyed end-to-end to Starfish/ACB. The B7's panel capabilities alone do not establish this app's HDR pipeline. Dolby Vision is a separate format path. | Unverified and disabled. The app exposes an Auto/SDR policy UI but its effective output remains the known SDR path. |
| Presented FPS | `FRAMEREADY` callbacks are throttled by firmware. Accepted `Feed` calls do not establish presentation time. | Unmeasurable with current API; dashboard labels it unavailable. |

The fork starts from the pinned DNS-SD feature masks `0x5A7FFEE6` and `0x00000000`, then explicitly clears bits 0, 4 and 42 and sets bit 27. The effective masks remain `0x5A7FFEE6` / `0x00000000`. The default mask may contain legacy photo, metadata and audio feature claims that this fork does not render independently; the table above reflects actual callbacks and playback code, rather than trusting bit names as proof of support. Changing those historical bits could affect working sender discovery and pairing, so this phase does not alter them.

The B7 is known to decode H.264 720p/30 through Starfish/ACB. Phase 2 enables a selectable 1080p/30 advertisement, 2 MiB video packets and Starfish source buffer, and an 8 MiB queue. The receiver checks the actual H.264 SPS dimensions against the selected profile and shows them independently of the advertisement. A sender may still send 720p after a 1080p advertisement; that is reported as 720p input. There is no B7 1080p negotiation trace or sustained hardware playback test yet. 60 FPS, 4K and HDR remain disabled pending separate end-to-end validation.

The on-screen diagnostics use SDL, while decoded video is drawn on a Starfish/ACB hardware plane. Layer order on Rockhopper 3.9.0 has not been confirmed. The idle dashboard is reliable because no video plane is active; a during-playback SDL overlay is an experiment until checked on the TV. No figure on that dashboard is labeled displayed FPS.
