# AirPlay and B7 media capabilities (Milestone 7)

This assessment is for the fork at the pinned UxPlay 1.74 source commit `9f3c2bbc658645533fa1057e76c29ec8c947fa0f`, on LG OLED B7 / Rockhopper 3.9.0. A sender's ability to connect is evidence for that interaction, not certification of every feature associated with an AirPlay version.

| Path | Current implementation and evidence | Status |
| --- | --- | --- |
| Screen Mirroring | Resolution, codec and maximum frame rate are independent settings. The receiver advertises H.264 at 720p/1080p, with optional HEVC alongside H.264 through AirPlay bit 42 up to 4K. The sender chooses actual codec, dimensions and rate; the receiver does not duplicate frames. | H.264 720p/1080p and HEVC 4K/30 mirror confirmed on owner's B7. 60 FPS is newly advertised as experimental and awaits B7 verification. On the tested B7, iOS still sends H.264 when HEVC mode is enabled at 720p/1080p; HEVC at those resolutions is not available as a forced choice. |
| AirPlay audio | The RAOP audio callback accepts PCM and compressed audio codes; the app decodes ALAC, AAC-LC and AAC-ELD with pinned FFmpeg and feeds 44.1 kHz stereo PCM to Starfish. Mirroring audio works on B7. Audio-only sessions have no playback startup path in this fork: `main.cpp` waits for a video keyframe. | Mirroring audio works; standalone audio-only playback unsupported. |
| AirPlay 2 | The pinned UxPlay core has partial modern pairing/mirroring/audio protocol support. This fork sets feature bit 27 (legacy pairing), enables bit 42 only with the experimental HEVC setting, and does not implement CoreUtils pairing, PTP, AirPlay 2 video queue or multiroom behavior. | Partial compatibility with modern senders; **not** full AirPlay 2. |
| Direct photo/video streaming | `raop.c` logs “ignoring AirPlay video streaming request (use option -hls to activate HLS support)” when the HLS switch is false. This fork never enables it, has no direct-media playback/render callbacks, and advertises video/HLS feature bits 0 and 4 as off. | Unsupported. Photos/video visible during mirroring use the mirroring path. |
| HLS | Pinned upstream UxPlay offers `-hls` with documented YouTube-app HLS support, using a GStreamer player. This fork does not enable that path or package a player for it. HLS is not equivalent to all Photos-app or AirPlay 2 direct-media requests. | Unsupported; requires separate design and firmware testing. |
| HEVC / 4K | An opt-in development setting enables bit 42 and a bounded HEVC Main 8-bit mirror path through Starfish/ACB. The owner confirmed visible HEVC 4K/30 AirPlay mirroring, Photos/video through mirroring, about 30 FPS Feed, and `LOADCOMPLETED`/`PLAYING` callbacks on the B7. Input SPS, Starfish video-info, logical app graphics window and requested ACB window are distinct; none alone establishes physical scanout resolution. H.264 remains the default. | Experimental mirroring verified on B7; native UHD output unmeasured. See [Milestone 6](MILESTONE6.md) and [Milestone 8](MILESTONE8.md). |
| HEVC Main10 / HDR10, HLG, BT.2020, Dolby Vision | Main10 is detected and rejected before Starfish Load. Public API evidence does not establish an HDR metadata payload contract for the B7's Starfish 3.9 `BUFFERSTREAM` path; no metadata is propagated to the decoder or output. LG's TV format support does not establish an app-level contract. | Disabled by default and unavailable in the UI. HDR10 is not claimed. See [Milestone 8](MILESTONE8.md). |
| Presented FPS | Incoming access units, PTS cadence, accepted Starfish Feed calls and firmware `FRAMEREADY` callback rate are reported separately. `FRAMEREADY` may be throttled and is not a reliable panel presentation counter. | Displayed FPS is unmeasurable with current API. 60 FPS sender and Feed rates are unverified on B7. See [Milestone 9](MILESTONE9.md). |

The [Milestone 5A HEVC audit](MILESTONE5.md) records the pre-probe baseline. The isolated B7 probe accepted HEVC Main 8-bit 3840×2160 through the Starfish API; [Milestone 6](MILESTONE6.md) describes the opt-in AirPlay integration, owner-confirmed mirroring, and remaining native-output uncertainty.

The fork starts from the pinned DNS-SD feature masks `0x5A7FFEE6` and `0x00000000`, then clears bits 0 and 4, sets bit 27, and sets bit 42 only when experimental HEVC is enabled. The default masks remain `0x5A7FFEE6` / `0x00000000`. **Photo bit 1, slideshow bit 5 and photo-caching bit 13 are already set even though no direct-photo handler exists.** They are inherited claims, not evidence of working photo transfer. Changing them could affect working sender discovery and pairing, so this phase does not alter them. The [Milestone 4E audit](MILESTONE4E.md) explains the 4D `/info` observation, missing upload/authorization path and unverified native 4K display surface.

The owner has verified H.264 1080p/30 through Starfish/ACB on the B7, including actual 1920×1080 SPS and no reported drops. The receiver checks SPS dimensions against the selected profile and shows them independently of the advertisement. A sender that sends 720p after a 1080p advertisement is reported as 720p input. The 1080p profile has 2 MiB video packets/source buffer and an 8 MiB queue; 720p remains the safe default. Experimental HEVC 4K/30 mirroring is also owner-confirmed; HEVC at 720p/1080p, native 4K output, 60 FPS and HDR remain unverified or disabled. See the [Phase 4B assessment](MILESTONE4.md) for direct-media blockers.

The owner verified that the SDL diagnostic overlay is visible during playback on the B7. It still does not measure panel presentation; no figure on the dashboard is labeled displayed FPS. HEVC at 720p/1080p remains a test target; the confirmed HEVC case is 4K/30 SDR mirroring.
