# Milestone 5E: experimental UHD HEVC control-path probe

The owner remotely observed the separate 0.1.1 HEVC probe complete its 1080p API control path on an LG B7 running Rockhopper 3.9.0: 30/30 access units accepted, seven `FRAMEREADY` callbacks, Starfish video-info 1920×1080, zero reported errors, and exit code zero. No one observed the panel, so decoded-picture and visible-output evidence remain incomplete.

## How the 0.1.2 UHD gate works

An explicit `mode=uhd` launch **first runs the packaged 1080p sample again** in the same process. Only `control-path=COMPLETE` **and successful Starfish/ACB teardown** from that fresh run permit the separate packaged 3840×2160/30 HEVC Main 8-bit SDR sample to start. The fresh control-path check requires all 30 access units accepted, matching video-info dimensions, Starfish playing state, an attempted ACB playing transition, accepted EOS, no error or stop signal, and successful teardown. The old `1080p-decoder-pass.flag` is never read. A failed or interrupted 1080p run blocks UHD and returns nonzero. A 500 ms pause follows successful 1080p teardown before UHD initialization. The 45-second hard watchdog covers both phases, including the pause. Each phase has its own Starfish/ACB lifecycle, bounded input buffer, 10 Feed retries per access unit, EOS handling and cleanup; the first sample's memory is released before the second is loaded.

The log markers `phase-begin name=fresh-1080p-gate`, `uhd-gate=passed`, and `phase-begin name=experimental-uhd` show the ordering. Each phase reports parsed SPS dimensions and bit depth, Starfish video-info, ACB transitions, accepted Feed count and retries, `FRAMEREADY` callback count, EOS, process RSS and cleanup. `control-path=COMPLETE` means the API path accepted the sample and reached the expected states. It **does not prove decoded pictures, visible video, native UHD presentation or a 3840×2160 output plane**. `decoder-path=UNPROVEN` remains explicit. `mode=1080p` retains its single 1080p case. No AirPlay receiver source, advertised feature bit, HDR, Main10, firmware or system library changes are part of this experiment.

The pre-existing package contains both a 1080p and UHD sample. They are independently generated by `tools/generate-hevc-samples.sh` and verified by the native parser and package checks. The UHD sample is used only when explicitly requested and after the current-launch gate succeeds.

## Remote manual procedure, rooted SSH and Luna

Download the successful `hevc-probe-armv7-<commit>` artifact from GitHub Actions. Extract it on Windows and verify `SHA256SUMS` against the files you will transfer. Keep the working 0.1.1 probe IPK for rollback. Close any active UxPlay receiver session; do not run the receiver and probe concurrently. On the TV, confirm `pidof hevc-probe` reports no process.

From Windows PowerShell, copy **only this separate probe** IPK to the TV and open a rooted SSH shell, replacing the placeholders:

```powershell
scp -i C:\path\to\tv-key .\com.github.danlflh.uxplaywebos.hevcprobe_0.1.2_arm.ipk root@TV_IP:/tmp/
ssh -i C:\path\to\tv-key root@TV_IP
```

On the TV, install the local file with Luna. Wait for the install service's completion response; a request acknowledgement alone is not confirmation that the package replaced 0.1.1. The [appInstallService `dev/install` documentation](https://www.webosose.org/docs/reference/ls2-api/com-webos-appinstallservice/) describes this call, although its exact behavior on Rockhopper must be judged from the TV response:

```sh
luna-send -i -f luna://com.webos.appInstallService/dev/install '{"id":"com.github.danlflh.uxplaywebos.hevcprobe","ipkUrl":"/tmp/com.github.danlflh.uxplaywebos.hevcprobe_0.1.2_arm.ipk","subscribe":true}'
```

Launch only when ready to test the hardware. This command runs a **fresh 1080p gate followed by UHD only if that gate passes**:

```sh
luna-send -n 1 -f luna://com.webos.applicationManager/launch '{"id":"com.github.danlflh.uxplaywebos.hevcprobe","params":{"mode":"uhd"}}'
```

Wait for the finite probe to exit. Then extract the log from the path that exists on this TV (the startup marker identifies `log=app` or `log=tmp`):

```sh
APP=com.github.danlflh.uxplaywebos.hevcprobe
for FILE in \
  "/var/palm/jail/$APP/media/developer/apps/usr/palm/applications/$APP/hevc-probe.log" \
  "/media/developer/apps/usr/palm/applications/$APP/hevc-probe.log" \
  "/media/cryptofs/apps/usr/palm/applications/$APP/hevc-probe.log" \
  "/var/palm/jail/$APP/tmp/uxplay-hevc-probe.log" \
  /tmp/uxplay-hevc-probe.log; do
  if test -f "$FILE"; then echo "LOG=$FILE"; tail -n 350 "$FILE"; fi
done
```

Report both phase summaries, especially `sample-valid`, `load-return`, `acb-sink-raw`, `acb-playing-state-raw`, `feed-stop`, `result`, `control-path`, `uhd-gate`, `eos-accepted`, cleanup and final `exit`. Also report whether any independent output-plane measurement was available. Without that measurement, a 3840×2160 SPS or video-info event is input metadata only. Do not use this result to enable AirPlay HEVC, HDR or 4K advertising.

For rollback, wait for the probe to exit (or send `kill -TERM <exact-probe-PID>` after checking `pidof hevc-probe`), copy the saved 0.1.1 IPK to `/tmp`, and invoke the same `dev/install` call with its 0.1.1 filename. If the install service refuses a version downgrade, remove **only** `com.github.danlflh.uxplaywebos.hevcprobe` with `luna://com.webos.appInstallService/dev/remove`, then reinstall 0.1.1. This probe has no pairing or receiver state; leave `com.github.danlflh.uxplaywebos.dev` untouched. If ACB remains busy after a forced stop, manually restart `AcbService` or reboot; the probe does not do either automatically.
